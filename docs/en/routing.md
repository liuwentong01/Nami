# Routing system principle



Nami's routing system is responsible for mapping URLs to page components and uses the same routing configuration for server-side rendering, ISR caching, data prefetching API, client-side lazy loading, and navigation prefetching.



When reading this chapter, you must first distinguish between three sets of "route selection" logic:



1. **Server-side HTML / ISR / data API matching**: use `matchConfiguredRoute()` uniformly, and use `rankRoutes + matchPath` internally.
2. **Client page rendering**: `NamiRouter` is based on `react-router-dom` v6, rendering `NamiRoute[]` into `<Routes>/<Route>`.
3. **Client-side prefetch**: `prefetchRoute()` uses the `generatedRouteDefinitions` generated by the build to scan sequentially, and then calls the dynamic import factory.



These three links use the same routing configuration, but the implementation details are not identical. The documentation will mark the differences where appropriate.

## 2. Routing configuration



Source code location: `packages/shared/src/types/route.ts`



Fields of `NamiRoute`:



```typescript
export interface NamiRoute {
  path: string;
  component: string;
  renderMode: RenderMode;
  getServerSideProps?: string;
  getStaticProps?: string;
  getStaticPaths?: string;
  revalidate?: number;
  fallback?: ISRFallbackStrategy;
  skeleton?: string;
  errorBoundary?: string;
  meta?: Record<string, unknown>;
  children?: NamiRoute[];
  exact?: boolean;
}
```



Field semantics:



| Field | Description |
|------|------|
| `path` | Routing path mode, supports static segments, dynamic parameters, constraint parameters, wildcards |
| `component` | Page component path, relative to `srcDir` |
| `renderMode` | Route rendering mode, the merged runtime configuration must have a value |
| `getServerSideProps` | Export name string of SSR data function |
| `getStaticProps` | SSG/ISR Export name string of data function |
| `getStaticPaths` | SSG/ISR Export name string of dynamic path function |
| `revalidate` | ISR route-level interval; a non-negative finite integer in seconds. `0` skips persistent CacheStore reads/writes, clears the old key, and keeps only same-process in-flight coalescing |
| `fallback` | ISR/SSG Dynamic path evasion strategy |
| `skeleton` | Level 3 static-emergency marker; currently only its presence is checked, with no component loading or route-chunk loading behavior |
| `errorBoundary` | Custom error boundary component path, reserved at the type level |
| `meta` | Routing meta information, such as `title`, `description`, `streaming`, `cacheTags` |
| `children` | Nested routing |
| `exact` | Whether to match exactly; prefix matching only when `exact === false` |



Example:



```typescript
export default defineConfig({
  routes: [
    { path: '/', component: './pages/home', renderMode: 'ssr' },

    {
      path: '/users/:id',
      component: './pages/user-detail',
      renderMode: 'ssr',
      getServerSideProps: 'getServerSideProps',
    },

    {
      path: '/posts/:id(\\d+)',
      component: './pages/post-detail',
      renderMode: 'ssr',
    },

    {
      path: '/docs/*',
      component: './pages/docs',
      renderMode: 'csr',
    },

    {
      path: '/products/:slug',
      component: './pages/product',
      renderMode: 'isr',
      revalidate: 60,
      getStaticProps: 'getStaticProps',
      getStaticPaths: 'getStaticPaths',
      meta: { cacheTags: ['product'] },
    },
  ],
});
```



`getServerSideProps`, `getStaticProps`, `getStaticPaths` are all **exported function name strings**, not function references. The framework runtime will use `ModuleLoader` to find the corresponding export by name from the server bundle.

## 3. Path matcher



Source code location: `packages/core/src/router/path-matcher.ts`



Nami comes with a path-to-regexp style matcher with no external dependencies. Core API:



| API | Function |
|-----|------|
| `compilePath(pattern, options)` | Compile path patterns into matching functions |
| `matchPath(pattern, pathname, options)` | Quick matching |
| `rankRoutes(routes)` | Sort by route specificity |



### Supported path syntax



| Syntax | Examples | Description |
|------|------|------|
| static path | `/about` | literal match |
| Required parameters | `/user/:id` | Match a single path segment, output `{ id }` |
| Optional parameters | `/user/:id?` | The entire parameter section can be omitted |
| Constraint parameters | `/post/:id(\\d+)` | Parameters must satisfy the regular rules in brackets |
| Multi-valued parameter | `/docs/:path+` | Matches one or more path segments |
| Wildcard | `/docs/*` | Matches remaining paths, parameter name is `'*'` |
| Regular grouping | `/file/(.*)` | Regular grouping parameters are named `$0`, `$1` |



Note: `*` in `/docs/*` compiles to `(.+)`, which requires at least one subsequent path segment, so it does not match `/docs` itself.

### Reverse path generation for dynamic SSG

At build time, `SSGRenderer` reuses the same token set and defines the corresponding
`getStaticPaths.params` keys: named, optional, constrained, and `+` parameters use
their names, `*` uses `'*'`, and regular-expression groups use `$0`, `$1`, and so on.
Nami does not perform string replacement. It segment-encodes params, materializes a
canonical URL, and then calls `matchPath(..., { exact: true })` to verify both the
match and parameter-value round trip.

A missing required parameter, `/` in a single-segment value, a constraint mismatch,
a generated URL that does not match, or two pages mapping to the same final static
file is a build error. The URL-to-file mapping itself is unchanged: `/blog/hello`
still writes `dist/static/blog/hello.html` plus its `.html.nami.json` sidecar.



### Standardization and compilation caching



`compilePath()` will pass `normalizePath()` before matching:



1. Make sure the path starts with `/`.
2. Remove `#hash`.
3. Remove `?query`.



The compilation results are stored in module-level `ruleCache`, and the cache keys include `pattern`, `exact`, and `sensitive`. The upper limit is `1024`. When it exceeds, the first half of the keys will be deleted to avoid unlimited growth.



The default is case-insensitive because regular flags use `i`. Exact matching allows optional trailing `/` by default:



```typescript
exact ? /^pattern\/?$/i : /^pattern/i
```



### `exact`



| Configuration | Regular Pattern | Behavior |
|------|----------|------|
| `exact !== false` | `^...\\/?$` | Exact match, trailing slash allowed |
| `exact === false` | `^...` | Prefix matching |



`exact: false` will cause the parent path to hit more URLs and should be used with caution in combination with sub-routes and overlapping routes.

## 4. Route priority sorting



Source code location: `packages/core/src/router/path-matcher.ts`



`rankRoutes()` does not simply match according to the configuration order, but counts the points first:



| Segment Type | Score | Example |
|--------|------|------|
| Static segment | `+3` | `/users` |
| Constraint parameters | `+2` | `/:id(\\d+)` |
| Common dynamic parameters | `+1` | `/:id` |
| Wildcard / multi-valued parameters | `+0` | `/*`, `:path+` |
| Mode without `*` | `+1` | Accuracy bonus |



Sorting rules:



1. Those with higher scores come first.
2. The scores are the same, the path segments are more advanced.
3. Still the same, keep the original order.



Example:



```text
/users/me static + static + no wildcard = 3 + 3 + 1 = 7
/users/:id(\\d+) static + constraints + no wildcards = 3 + 2 + 1 = 6
/users/:id static + dynamic + no wildcard = 3 + 1 + 1 = 5
/users/* static + wildcard = 3 + 0 = 3
```



Therefore, `/users/123` hits `/users/:id(\\d+)` first, and `/users/me` hits the static route first.

## 5. Uniform matching on the server side



Source code location: `packages/server/src/middleware/route-match.ts`



Server-side unified entrance:



```typescript
export function matchConfiguredRoute(
  requestPath: string,
  routes: NamiRoute[],
): RouteMatchResult | null;
```



Process:



```text
matchConfiguredRoute(path, routes)
  -> matchRouteList(path, routes)
       -> sortedRoutes = rankRoutes(routes)
       -> matchPath(route.path, path, { exact: route.exact !== false })
       -> If hit, return { route, params, isExact }
       -> If the top level misses, scan children recursively
```



This function is shared by three types of server-side middleware:



| Middleware | Purpose |
|--------|------|
| `isr-cache-middleware.ts` | Determine whether the request is an ISR route and decide whether to cache |
| `data-prefetch-middleware.ts` | Matches the page route corresponding to `/_nami/data/*` |
| `render-middleware.ts` | Create `RenderContext` and select Renderer |



Unified matching sources avoid the problem of "the cache layer hits route A and the rendering layer hits route B".



### Meaning of `isExact`



`RouteMatchResult.isExact` is currently controlled by:



```typescript
const exact = route.exact !== false;
return { isExact: exact };
```



derived. It indicates whether the routing configuration matches an exact pattern, but does not indicate "whether this URL has exactly no extra segments."

## 6. Client routing



Source code location: `packages/client/src/router/nami-router.tsx`



Client uses `react-router-dom` v6:



```text
wrapApp wrappers
  → ClientErrorBoundary
       → BrowserRouter
            → NamiDataProvider
                 ├─ RouteChangeListener
                 ├─ NamiHead
                 └─ Routes → Route → Suspense → Page
```



Each `NamiRoute` will be converted to `<Route>`. Component loading process:



```text
route.component
  -> componentResolver(componentPath)
  -> generatedComponentLoaders[componentPath]
  -> React.lazy()
  -> Suspense
```



The default `componentResolver` reads the `generatedComponentLoaders` generated at build time. If the corresponding loader cannot be found, rejected Promise will be returned and "Routing component loader not found" will be recorded.



`NamiRouter` has `lazyComponentCache` internally, and `componentResolver + componentPath` caches `React.lazy` to wrap the results to avoid re-creating lazy components every time it is rendered, while allowing testing, HMR or multiple application scenarios to replace the resolver and get a new component loader.



### Client routing changes



`RouteChangeListener` uses `useLocation()` to listen for the complete `pathname + search + hash`:



```text
from = previousPathRef.current
to = location.pathname + location.search + location.hash
onRouteChange({ from, to }) is triggered when from !== to
```



`entry-client.tsx` will call the plug-in after receiving it:



```typescript
pluginManager.runParallelHook('onRouteChange', {
  from,
  to,
  params: {},
});
```



The `params` currently passed to the plugin is always an empty object. If the plug-in requires dynamic parameters, it needs to be parsed separately based on the routing context.



### Differences in routing between client and server



Server-side explicit `rankRoutes()`; final matching of client-side `<Routes>` is done by React Router v6, `NamiRouter` is rendered as passed in `routes.map(renderRoute)`. Most standard routes behave consistently, but you should avoid relying on "configuration order" to infer server-side behavior when there are large numbers of overlapping routes, `exact: false`, wildcards, or nested routes.

## 7. Build and generate routing module



Source code location: `packages/webpack/src/configs/client.config.ts`



The client build produces:



```text
.nami/generated-route-modules.ts
```



Export two objects:



```typescript
export const generatedComponentLoaders = {
  "./pages/home": () => import(/* webpackChunkName: "route-pages-home" */ "..."),
} as Record<string, () => Promise<unknown>>;

export const generatedRouteDefinitions = [
  { path: "/", component: "./pages/home", exact: true },
];
```



The generation logic comes from `ensureGeneratedRouteModules()`:



| Products | Sources |
|------|------|
| `generatedComponentLoaders` | `config.routes.map(route => route.component)` Remove duplicates |
| `generatedRouteDefinitions` | `config.routes.map(route => ({ path, component, exact }))` |
| `exact` | `route.exact === false ? false : true` |



The current generation logic only scans the top-level `config.routes` and does not recursively collect `children`. If the sub-route has an independent `component`, the default generation module may lack the corresponding loader, and the client-side prefetching or rendering will not find the component mapping. When using nested routing, you need to confirm the build result, or complete it by customizing `componentResolver`.

## 8. `NamiLink` and route prefetching



Source code location:



- `packages/client/src/router/link.tsx`
- `packages/client/src/router/route-prefetch.ts`



`NamiLink` is an enhanced version of `Link` of `react-router-dom`:



```tsx
<NamiLink to="/about" prefetchOnHover>
  About
</NamiLink>

<NamiLink to="/products" prefetchOnVisible prefetchMargin="200px">
  Products
</NamiLink>
```



Add new props:



| Fields | Default Values | Behavior |
|------|--------|------|
| `prefetchOnHover` | `false` | Trigger prefetch on mouseover |
| `prefetchOnVisible` | `false` | Trigger prefetch after entering the viewport |
| `prefetchMargin` | `'100px'` | `IntersectionObserver.rootMargin` |
| `prefetchDelay` | `100` | hover delay, set to `0` for immediate prefetching |



`NamiLink` internal call:



```typescript
prefetchRoute(targetPath)
```



No options are passed, so by default only JS chunks are prefetched and no data is prefetched.



### `prefetchRoute()`



Default options:



```typescript
{
  prefetchChunk: true,
  prefetchData: false,
  dataApiPrefix: NAMI_DATA_API_PREFIX,
  timeout: 5000,
}
```



Process:



```text
prefetchRoute(path)
  -> prefetchChunkForRoute(path)
       -> resolveRouteComponent(path)
       -> generatedRouteDefinitions sequential scan matchPath
       -> generatedComponentLoaders[componentPath]()
  -> if prefetchData: true
       -> GET `${dataApiPrefix}${path}`
       -> Store in dataCache, TTL 5 minutes
  -> Promise.race([allSettled(tasks), timeout])
```



The prefetch failure of `prefetchRoute()` only records warn and does not block user navigation.



### Path extraction



`NamiLink`'s `to` supports strings or objects. In object form:



```typescript
return `${to.pathname ?? '/'}${to.search ?? ''}${to.hash ?? ''}`;
```



The path used for prefetching will contain `search` and `hash`, so the object form `to={{ pathname, search, hash }}` is consistent with the real navigation target, and prefetch deduplication is also calculated as a complete target.

## 9. `useRouter`



Source code location: `packages/client/src/router/use-router.ts`



`useRouter()` encapsulates `react-router-dom`:



```typescript
const router = useRouter();

router.path;      // location.pathname
router.fullPath;  // pathname + search + hash
router.query;     // Convert URLSearchParams to a plain object
router.params;    // useParams()
router.hash;      // location.hash

router.push('/dashboard');
router.replace('/login');
router.back();
router.forward();
router.go(-2);
```



Query parameters use `URLSearchParams.forEach()` to convert objects. Multi-valued parameters with the same name will retain the last value.



Navigation method:



| Method | Implementation |
|------|------|
| `push(path, { state })` | `navigate(path, { state })` |
| `replace(path, { state })` | `navigate(path, { replace: true, state })` |
| `back()` | `navigate(-1)` |
| `forward()` | `navigate(1)` |
| `go(delta)` | `navigate(delta)` |



`useRouter` currently does not have a built-in `prefetch` method; for prefetching, please use `NamiLink` or call `prefetchRoute()` directly.

## 10. `lazyRoute`



Source code location: `packages/core/src/router/lazy-route.ts`



`lazyRoute()` is a lightweight wrapper for `React.lazy + Suspense`:



```typescript
const About = lazyRoute(
  () => import('./pages/about'),
  {
    loading: <div>Loading...</div>,
    errorFallback: <div>Page failed to load</div>,
  },
);

<About.Component />;
await About.preload();
```



Implementation points:



| Mechanism | Behavior |
|------|------|
| `cachedImport()` | Cache import Promise to avoid repeated loading |
| Import failed | Clear the cache and allow retry next time |
| `Suspense` | Loading showing `loading` |
| `LazyErrorBoundary` | Only wrapped if `errorFallback` is provided |
| `preload()` | Call `cachedImport()` in advance. If it fails, only warn and not throw it to the caller |



The default `NamiRouter` already uses `React.lazy + Suspense` to load components. `lazyRoute()` is more suitable for users to use manually in custom routing components or local dynamic components.

## 11. Data prefetching API



Source code location: `packages/server/src/middleware/data-prefetch-middleware.ts`



Data API prefixes come from:



```typescript
NAMI_DATA_API_PREFIX = '/_nami/data'
```



Only handle GET requests:



```text
GET /_nami/data/products/123
  -> requestPath = /products/123
  -> matchConfiguredRoute(requestPath, config.routes)
  -> Press renderMode to call the data function
```



### SSR



Conditions:



```typescript
route.renderMode === RenderMode.SSR && route.getServerSideProps
```



Reads the exported function specified by `route.getServerSideProps` from the server bundle. Pass in context:



| Field | Source |
|------|------|
| `params` | Routing dynamic parameters |
| `query` | Koa query, keep only strings or string arrays |
| `headers` | Lowercase request header |
| `path` | Page path after removing `/_nami/data` |
| `url` | Page path + original querystring |
| `cookies` | Parsed from `Cookie` request header |
| `requestId` | `ctx.state.requestId` or `'unknown'` |



Return processing:



| Return | HTTP response |
|------|-----------|
| `notFound` | `404 { notFound: true }` |
| `redirect` | `statusCode` or `308/307`, body is `{ redirect }` |
| `props` | `200`, body is `props` |



### SSG / ISR



Conditions:



```typescript
(route.renderMode === SSG || route.renderMode === ISR)
  && route.getStaticProps
```



Call `getStaticProps({ params })`. The current data API link only transmits `params`, and does not transmit query, headers, cookies, and locale.



Return handling also supports `notFound` and `redirect`.

Keep the JSON API separate from the Core HTML contract. In the SSG/ISR build and
render paths, GSP validates an explicit redirect status as one of
`301/302/303/307/308`; omission resolves to permanent `308` or temporary `307`.
The current `/_nami/data/*` table merely exposes the data-function result, so this
whitelist must not be described as a global GSSP or data-API rule.



### No data function



If the hit routing pattern does not require data functions, or the corresponding functions are not configured:



```http
204 No Content
```



This JSON API and `window.__NAMI_DATA__` in the HTML first screen are two links. Data prefetching for HTML links occurs within a specific Renderer.

## 12. Notes on nested routing



Both the type and client `NamiRouter` support `children`, and the server `matchConfiguredRoute()` will also recursively match sub-routes. But the current build file only traverses the top-level `config.routes`:



```typescript
config.routes.map((route) => route.component)
config.routes.map((route) => ({ path, component, exact }))
```



This leads to two practical suggestions:



1. If the sub-route has independent components, you need to confirm whether `.nami/generated-route-modules.ts` contains it.
2. For complex nested routing, it is recommended to use flat routing configuration to express the complete path, or provide customized `componentResolver`.



In addition, React Router v6's nested routes usually require the parent component to render `<Outlet />` to display the child route content. `NamiRouter` is only responsible for generating the `<Route>` tree and will not automatically insert `<Outlet />` into the parent component.

## 13. Common misunderstandings



### Misunderstanding 1: The server matches exactly in the configuration order



No. The server first sorts using `rankRoutes()` and then matches them one by one. The original order only works if the fractions and number of segments are the same.



### Misunderstanding 2: Client-side prefetching and server-side matching must be exactly the same



uncertain. The server uses `rankRoutes()` explicitly; `prefetchRoute()` scans in array order on `generatedRouteDefinitions`; client page rendering is determined by React Router v6. Overlapping routes should be written as clearly as possible to avoid relying on edge ordering.



### Misunderstanding 3: `NamiLink` will prefetch data by default



No. `NamiLink` calls `prefetchRoute(path)` by default, only prefetching JS chunks. Data prefetching requires an explicit call to `prefetchRoute(path, { prefetchData: true })`.



### Misunderstanding 4: `children` will automatically enter the generation module



Not currently. `.nami/generated-route-modules.ts` is only generated based on the top-level `config.routes`.



### Misunderstanding 5: `/_nami/data/*` is the data prefetch entry for HTML SSR



No. It is an API for client-side routing to prefetch JSON. Data prefetching for HTML SSR is performed by `SSRRenderer.prefetchData()`.



### Misunderstanding 6: `getServerSideProps` fields can be passed to functions



No. What is passed in the routing configuration is the export function name string, such as `'getServerSideProps'`.
